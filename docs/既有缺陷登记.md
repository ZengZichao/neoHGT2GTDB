# 既有缺陷登记册（方案附录 F）

方案 §附录 F 列了 14 条"与 GTDB 适配同源"的既有缺陷，并建议"一并登记 issue"。这份文件
就是那份登记：每条给出**状态**、**证据位置**，以及仍然存在的缺陷的**复现方式**。
它同时被 `tools/verify_plan_traceability.py --defects` 机器核对，规则与
[`计划任务对照表.md`](计划任务对照表.md) 相同：

1. 附录 F 的每个 `F*` 编号必须且只能出现一次；
2. 状态只能取 `已修复` / `已按方案更正` / `登记未改`；
3. 引用的反引号路径必须真实存在；
4. `登记未改` 必须写清为什么不改与如何复现（不允许一句话糊过去）。

一条贯穿性原则：本适配对上游五个文件（`database.py`/`search.py`/`analyze.py`/`util.py`/
`config.yml`）的要求是**纯追加**（RT-1 逐行核对 `deleted_lines=0`），所以凡是"修它必须先改
上游已有行"的缺陷，都只在 GTDB/hybrid 分支上堵住，上游行为保持原样并在此登记。

## 不在方案附录 F 里的观察项（不占 F 编号，因而不进登记表核对）

登记门禁把这份文件里每一个四列表格的行首当作**方案附录 F 的编号**来核对（`docs/既有缺陷登记.md` 的 F1..F14 必须与方案一一对应，多出来的编号判 `不是方案编号` 并失败）。因此凡不是方案列出的缺陷，都写在这一节里而不是表格里：观察保留，编号不冒充方案的条目。

* **上游 `neoHGT/server.py` 在 import 时安装包。** `server.py:28-29` 定义 `install(package) = subprocess.check_call([sys.executable, "-m", "pip", "install", package])`，而 `:50` 在模块级的 `try: import requests / except: install('requests')` 里调用它。本项目禁止联网与安装系统包（安全规则 13），所以这条路径一次都不能被走到。实测：在整个适配（`neoHGT/*.py`、`tools/*.py`、`neoHGT/tests/*.py`、`.github/workflows/*.yml`）里 grep `import.*server` / `from neoHGT import server` **没有任何 importer**，故今天不可达；本轮也没有改它——改它要删除上游已有行，与 RT-1（零回归，上游文件纯追加）冲突。
  由此引出两条可操作的约束：谁若需要 import 这个模块，必须先确认 `requests` 可导入（本机实测可导入），或者在 GTDB 侧另建入口；本轮的归因探针 （`临时文件/r113_pip_attribution_probe.py`）因此刻意**不** import `neoHGT.server`，这一点写在探针文件里而不是只写在这里。
  顺带一条同轮的实测证据：`~/.cache/pip/selfcheck` 在门禁窗口内出现的新文件**不是我们写的** —— 四个门禁形状的命令在该目录下产生 0 个新文件，`commands.log` 七百来条记录里没有任何 pip 调用 （`缓存测试/reports/R52_pip_attribution.json`）。第五十二轮据此把 IT-7 的命名空间归责改成"豁免必须带证据"。

* **上游 `search.py` 的"批量 native 自比对"在 `-m precomp` 下是死分支。** `search.py:930-935` 写着 `batches = ([seqs] if self.method != 'precomp' else self.subset_seqs(seqs, self.queries, self.maxchars))`，意图清楚：预计算表路线下要按 `--queries/--maxchars` 分批来自比对。但这个分支要求 `self.aln_method == 'native'`，而 `:412-414` 在 `self.method == 'precomp'` 时把 `auto`/`native` 一律改写成 `fast`（内置算法），于是**该分支里 `self.method != 'precomp'` 恒真**，`subset_seqs` 那半边永远走不到；搜索侧同理，`:160-161` 在 precomp 下直接 `[seqs]`。后果是 `--queries`、`--maxchars`、`--extrargs` 三个选项在这条路线上被解析、被读进对象（`:305-306` 甚至向 config.yml 要 `precomp.queries` 这类键，而文件里没有 `precomp:` 段），却没有任何代码使用它们。
  本轮没有去"修好"这个分支：让它可达要改写 `:412-414` 的方法选择，那会改变 NCBI 路线上自比对的分批与结果，与 RT-1（上游文件纯追加、NCBI 夹具逐字节一致）正面冲突，而且"该不该分批"是科学口径问题、不是笔误。GTDB 路线因此改为**明确拒绝**这三个选项（`neoHGT/search.py::guard_precomp_knobs`，调用点 `set_params_gtdb`），并把"为什么这三条读取落不了地"写成 `docs/交付物清单.md` 的「动态配置段的可达性」一行，由登记门禁第 23 条核对那行拒绝是否还点名着这三个选项。上游若哪天想让它们生效，需要同时删掉本行的申明——门禁会在拒绝语消失时立即报红，而不是让死分支继续假装可配置。
  普查证据：`缓存测试/reports/R54_entry_expansion.json`（73 条入口串读取中，指向文件里不存在之段的只剩 `auto.*` 与 `precomp.*` 六条）与 `缓存测试/reports/R54_config_reads_precision.json`（下标读法与入口串读法两个集合完全不相交）。
