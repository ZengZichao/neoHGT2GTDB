# Known-defects register (Plan Appendix F)

Plan Appendix F lists 14 pre-existing defects "of the same origin as the GTDB adaptation" and suggests "registering them together as issues". This document
is that register: each entry is given its **status**, the **location of its evidence**, and, for defects that still exist, the **way to reproduce** it.
It is also machine-checked by `tools/verify_plan_traceability.py --defects`, under the same rules as
[`计划任务对照表.md`](计划任务对照表.md):

1. Every `F*` number of Appendix F must appear exactly once;
2. Status may only take `已修复` / `已按方案更正` / `登记未改`;
3. The referenced backtick paths must really exist;
4. A `登记未改` entry must state clearly why it was not changed and how to reproduce it (one vague sentence is not allowed).

One principle runs through the whole thing: this adaptation requires the five upstream files (`database.py`/`search.py`/`analyze.py`/`util.py`/
`config.yml`) to be **purely additive** (RT-1 checks `deleted_lines=0` line by line), so every defect whose "fix requires first changing
an existing upstream line" is plugged only on the GTDB/hybrid branch, upstream behavior is kept as-is, and it is registered here.

## Observations not in Plan Appendix F (they take no F numbers and are therefore not checked by the register-table gate)

The register gate treats the leading cell of every four-column table in this document as a **Plan Appendix F number** and checks it (the F1..F14 of `docs/既有缺陷登记.md` must map one-to-one onto the plan; any extra number is judged `不是方案编号` and fails). Therefore everything that is not a defect listed by the plan is written in this section rather than in the table: the observations are kept, and their numbering does not pass itself off as the plan's entries.

* **Upstream `neoHGT/server.py` installs packages at import time.** `server.py:28-29` defines `install(package) = subprocess.check_call([sys.executable, "-m", "pip", "install", package])`, and `:50` calls it inside a module-level `try: import requests / except: install('requests')`. This project forbids network access and installing system packages (security rule 13), so this path must never be reached even once. Measured: grepping `import.*server` / `from neoHGT import server` across the whole adaptation (`neoHGT/*.py`, `tools/*.py`, `neoHGT/tests/*.py`, `.github/workflows/*.yml`) finds **no importer at all**, so today it is unreachable; this round did not change it either — changing it would require deleting existing upstream lines, conflicting with RT-1 (zero regression, upstream files purely additive).
  This yields two actionable constraints: whoever needs to import this module must first confirm that `requests` is importable (measured importable on this machine), or build a separate entry point on the GTDB side; this round's attribution probe (`临时文件/r113_pip_attribution_probe.py`) therefore deliberately does **not** import `neoHGT.server`, and that fact is written in the probe file itself, not only here.
  One more measured piece of evidence from the same round: the new files that appeared under `~/.cache/pip/selfcheck` within the gate window were **not written by us** — four gate-shaped commands produced 0 new files in that directory, and among the roughly seven hundred records in `commands.log` there is not a single pip call (`缓存测试/reports/R52_pip_attribution.json`). On that basis Round 52 changed IT-7's namespace attribution to "exemptions must carry evidence".

* **Upstream `search.py`'s "batched native self-alignment" is a dead branch under `-m precomp`.** `search.py:930-935` reads `batches = ([seqs] if self.method != 'precomp' else self.subset_seqs(seqs, self.queries, self.maxchars))`; the intent is clear: on the precomputed-table route, self-alignment should be batched according to `--queries/--maxchars`. But this branch requires `self.aln_method == 'native'`, while `:412-414` rewrites both `auto`/`native` into `fast` (the built-in algorithm) whenever `self.method == 'precomp'`, so **within this branch `self.method != 'precomp'` is always true** and the `subset_seqs` half is never reached; the search side is the same, with `:160-161` taking `[seqs]` directly under precomp. The consequence is that the three options `--queries`, `--maxchars`, `--extrargs` are parsed and read into the object on this route (`:305-306` even asks config.yml for keys like `precomp.queries`, and the file has no `precomp:` section), yet no code ever uses them.
  This round did not try to "fix" that branch: making it reachable would require rewriting the method selection at `:412-414`, which would change how self-alignment is batched and what it produces on the NCBI route — a head-on conflict with RT-1 (upstream files purely additive, NCBI fixtures byte-identical) — and "whether to batch at all" is a question of scientific protocol, not a typo. The GTDB route therefore **explicitly rejects** these three options instead (`neoHGT/search.py::guard_precomp_knobs`, called from `set_params_gtdb`), and the reason "why these three reads cannot take effect" is written as the 「动态配置段的可达性」 line of `docs/交付物清单.md`, checked by clause 23 of the register gate for whether that rejection line still names these three options. If upstream ever wants them to take effect, it would have to delete this line's declaration at the same time — the gate turns red the moment the rejection wording disappears, instead of letting the dead branch keep pretending to be configurable.
  Survey evidence: `缓存测试/reports/R54_entry_expansion.json` (of 73 entry-string reads, only six remain that point to sections absent from the file — `auto.*` and `precomp.*`) and `缓存测试/reports/R54_config_reads_precision.json` (the subscript-style reads and the entry-string reads are two fully disjoint sets).
