# 方案 §10 验证矩阵核对（UT / IT / 科学有效性 / RT）

§10.2 的单元测试判据、§10.3 的集成测试场景、§10.4 的"到底更可信吗"四项证据、
§10.5 的回归与兼容项，是方案给出的**验证计划本身**。这份文件逐条写明每条编号由哪个用例
或哪份证据覆盖，接受 `tools/verify_plan_traceability.py` 的机器核对（与其余九张登记表同一套
规则）：

1. 四张表里的每个编号必须且只能出现一次，登记表中不得出现方案里没有的编号；
2. 状态只能取 `已覆盖` / `部分覆盖` / `未覆盖`，后两种必须写清缺的是哪一半；
3. 引用的反引号路径（可带 `:行号`）必须真实存在，行号不得超出文件长度；指向测试文件的引用一律写成 `路径::符号` 形态，门禁会确认该文件里真的有这个 `def` / `class`——第二十轮的实测教训是：往测试文件里插一条用例，就会让所有行号引用静默错位，而这种错位恰好不会被"路径存在"的检查发现。

写这张表的动机是第十五轮的一次清点：§10.1 要求的派生夹具当时并不存在，而 `search`/`analyze`
的 GTDB 分支从未有任何**离线**用例真正跑过。把验证矩阵摊开成可核对的表，就是为了不再出现
"计划里写了、代码里其实没有"这种静默缺口。

方案里 §10.4 是一个有序列表而不是表格，所以它的编号在这里写作 `10.4-<n>`（与 §10.4 里
"第 n 条"一一对应）；没有稳定编号就无法登记，也就无法门禁。
